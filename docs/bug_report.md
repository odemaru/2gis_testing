# Баг-репорт: метод создания избранного места

- **Проект:** REST API сервиса избранных мест 2GIS
- **Тестируемый метод:** `POST /v1/favorites`
- **Стенд:** https://regions-test.2gis.com/v1
- **Автор:** Гавриков Т. М.
- **Дата проверки:** 24.08.2026
- **Окружение:** macOS 15, Python 3.12, pytest 8.4.1, requests 2.32.3

Найдено 6 дефектов. Каждый воспроизведён вручную через curl и закреплён
автотестом в [`tests/test_known_bugs.py`](../tests/test_known_bugs.py).

| ID | Кратко | Приоритет |
|----|--------|-----------|
| [BUG-1](#bug-1) | Принимается `title` длиной 1000 символов при пределе 999 | Средний |
| [BUG-2](#bug-2) | Токен действует дольше заявленных 2000 мс | Высокий |
| [BUG-3](#bug-3) | `500 Internal Server Error` на координатах `(0, 0)` | Высокий |
| [BUG-4](#bug-4) | Опечатка в тексте ошибки: «обзательным» | Низкий |
| [BUG-5](#bug-5) | `color` проверяется без учёта регистра | Средний |
| [BUG-6](#bug-6) | `created_at` опережает время сервера на час | Средний |

Во всех сценариях ниже токен получается так:

```bash
TOKEN=$(curl -s -D - -o /dev/null -X POST https://regions-test.2gis.com/v1/auth/tokens \
        | sed -n 's/.*token=\([a-f0-9]*\).*/\1/p')
```

<a id="bug-1"></a>
## BUG-1. Принимается `title` длиной 1000 символов

- **Приоритет:** Средний
- **Воспроизводимость:** 100 %
- **Автотест:** `test_title_of_1000_characters_is_rejected`

По документации максимальная длина названия 999 символов. Фактически сервис
принимает 1000, то есть в проверке длины ошибка на единицу.

### Шаги воспроизведения

```bash
curl -s -X POST https://regions-test.2gis.com/v1/favorites -b "token=$TOKEN" \
  --data-urlencode "title=$(printf 's%.0s' {1..1000})" \
  -d "lat=55.028254&lon=82.918501" -w "\nHTTP %{http_code}\n"
```

### Ожидаемый результат

`400 Bad Request`, сообщение `Параметр 'title' должен содержать не более 999 символов`.

### Фактический результат

`200 OK`, место создано, в ответе название из 1000 символов.

### Определение границы

| Длина `title` | Ответ |
|---------------|-------|
| 999 | 200 OK |
| **1000** | **200 OK**, ожидалось 400 |
| 1001 | 400 Bad Request |

<a id="bug-2"></a>
## BUG-2. Токен действует дольше заявленных 2000 мс

- **Приоритет:** Высокий
- **Воспроизводимость:** 100 %
- **Автотест:** `test_token_expires_after_documented_ttl`

По документации токен живёт 2000 мс, то же значение стоит в заголовке ответа
(`Set-Cookie: token=...; Max-Age=2`). Фактически сервис принимает токен
примерно на 700 мс дольше. Сессия остаётся рабочей после объявленного срока,
то есть ограничение доступа по времени работает слабее, чем заявлено.

### Шаги воспроизведения

1. Получить токен.
2. Выждать 2100 мс.
3. Отправить корректный запрос создания места с этим токеном.

### Ожидаемый результат

`401 Unauthorized`, сообщение `Передан несуществующий или «протухший» 'token'`.

### Фактический результат

`200 OK`, место создано.

### Определение границы

Пауза между получением токена и запросом увеличивалась последовательно:

| Пауза | Ответ |
|-------|-------|
| 2000 мс | 200 OK |
| 2500 мс | 200 OK |
| 2700 мс | 200 OK |
| **2800 мс** | **401 Unauthorized** |

Фактическое время жизни токена около 2700 мс вместо 2000 мс.

<a id="bug-3"></a>
## BUG-3. `500 Internal Server Error` на координатах `(0, 0)`

- **Приоритет:** Высокий
- **Воспроизводимость:** 100 %, 9 попыток из 9, включая разные формы записи нуля
- **Автотест:** `test_zero_coordinates_are_accepted`

Точка с координатами `(0, 0)` находится в Гвинейском заливе и попадает в оба
допустимых диапазона: `lat` от -90 до 90, `lon` от -180 до 180. Запрос с
такими координатами роняет сервис.

### Шаги воспроизведения

```bash
curl -s -X POST https://regions-test.2gis.com/v1/favorites -b "token=$TOKEN" \
  -d "title=test&lat=0&lon=0" -w "\nHTTP %{http_code}\n"
```

### Ожидаемый результат

`200 OK`, место создано с координатами `lat: 0, lon: 0`.

### Фактический результат

```
HTTP 500
Content-Type: text/plain; charset=utf-8

500 Internal Server Error

Server got itself in trouble
```

### Условие срабатывания

Ошибка возникает только когда **оба** параметра равны нулю. Ноль по одной
координате обрабатывается нормально:

| `lat` | `lon` | Ответ |
|-------|-------|-------|
| 0 | 0 | **500** |
| 0 | 82.918501 | 200 OK |
| 55.028254 | 0 | 200 OK |
| 0.000001 | 0.000001 | 200 OK |
| 0 | 0.000001 | 200 OK |

Форма записи нуля роли не играет: `0`, `0.0`, `-0`, `00` и `0e0` дают
одинаковый результат. Похоже, координаты где-то проверяются на заполненность,
а не на попадание в диапазон, и ноль при такой проверке считается пустым
значением.

### Дополнительно

Ответ приходит в `text/plain`, а не в JSON-конверте
`{"error": {"id": ..., "message": ...}}`, который сервис использует для
остальных ошибок. Клиент, который разбирает ответ как JSON, получит ошибку
разбора вместо понятного сообщения.

- **Воспроизводимость:** 100 %
- **Автотест:** `test_missing_title_error_message_is_spelled_correctly`

<a id="bug-5"></a>
## BUG-5. `color` проверяется без учёта регистра и сохраняется как прислали

- **Приоритет:** Средний
- **Воспроизводимость:** 100 %
- **Автотест:** `test_color_in_wrong_case_is_rejected`

По документации у `color` закрытый список значений: `BLUE`, `GREEN`, `RED`,
`YELLOW`. В сообщении об ошибке сервис перечисляет их же в верхнем регистре.
При этом значение в любом регистре принимается и сохраняется как есть.

### Шаги воспроизведения

```bash
curl -s -X POST https://regions-test.2gis.com/v1/favorites -b "token=$TOKEN" \
  -d "title=test&lat=55.028254&lon=82.918501&color=bLuE"
```

### Ожидаемый результат

`400 Bad Request`, сообщение
`Параметр 'color' может быть одним из следующих значений: BLUE, GREEN, RED, YELLOW`.

### Фактический результат

`200 OK`, в ответе `"color": "bLuE"`.

### Охват

Приняты все четыре цвета в нижнем и в смешанном регистре: `blue`, `Blue`,
`bLuE`, `green`, `red`, `yellow`. Значения вне списка (`test`, `BLUEGREEN`,
пустая строка) отклоняются правильно.

В итоге в хранилище попадают значения, которых нет в документации. Клиенту
приходится приводить регистр самому, а сравнение `color == "BLUE"` перестаёт
работать надёжно.

<a id="bug-6"></a>
## BUG-6. `created_at` опережает время сервера на час

- **Приоритет:** Средний
- **Воспроизводимость:** 100 %
- **Автотест:** `test_created_at_matches_server_time`

Поле `created_at` содержит дату создания в формате ISO 8601 и приходит со
смещением `+00:00`, то есть заявляет время по UTC. Фактическое значение
опережает время сервера ровно на час.

### Шаги воспроизведения

```bash
curl -s -D - -X POST https://regions-test.2gis.com/v1/favorites -b "token=$TOKEN" \
  -d "title=test&lat=55.028254&lon=82.918501"
```

Сравнить заголовок `Date` и поле `created_at` из **одного и того же** ответа.

### Ожидаемый результат

`created_at` совпадает с временем сервера с точностью до секунд.

### Фактический результат

```
Date: Mon, 24 Aug 2026 13:19:10 GMT
"created_at": "2026-08-24T14:19:10+00:00"
```

Разница ровно 1 час, при этом смещение указано нулевое. Похоже, записывается
локальное время сервера, а метка `+00:00` проставляется принудительно. Клиент,
который доверяет смещению, получит время создания на час вперёд.

## Прочие замечания

Ниже собраны расхождения, которые я не стал оформлять как дефекты. Работу
метода они не ломают, но расходятся с документацией или с ожиданиями от API.

### З-1. `title` принимает символы вне заявленного набора

По документации в названии допустимы латинские и кириллические символы, цифры
и знаки препинания. Фактически принимаются и сохраняются без изменений эмодзи
(`🏠 дом`), греческие буквы (`Δ`), перевод строки (`a\nb`) и HTML-разметка
(`<script>alert(1)</script>`). Хранение разметки без экранирования стоит
проверить отдельно на стороне клиентов, которые её показывают.

### З-2. Ответ `405` приходит не в формате ошибки сервиса

Обращение к `/v1/favorites` методами `GET`, `PUT`, `DELETE`, `PATCH`
возвращает `405: Method Not Allowed` в `text/plain`, а не в JSON-конверте
`{"error": {...}}`, принятом для остальных ошибок.

### З-3. Числа в экспоненциальной записи принимаются

`lat=5.5e1` принимается и сохраняется как `55.0`. В документации такое
поведение не описано.
